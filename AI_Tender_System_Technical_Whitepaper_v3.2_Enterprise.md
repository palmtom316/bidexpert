# AI 辅助投标系统

# 企业级技术白皮书 v3.2 (Resilience & Governance Enhanced)

------------------------------------------------------------------------

# 一、版本升级说明

v3.2 在 v3.1 Enterprise 基础上新增：

-   章节级异步编排架构优化
-   语义缓存安全约束方案
-   证据有效期与溯源增强
-   项目级与任务级预算控制体系
-   可控多步 RAG（Schema 驱动）
-   修订轨迹与版本差异机制

目标：

构建具备高韧性、强审计、可成本控制、可持续演进能力的企业级投标系统。

------------------------------------------------------------------------

# 二、架构韧性增强

## 2.1 章节级异步编排

采用 Celery 进行章节级任务拆分：

-   REQUIREMENT_EXTRACT 任务
-   SECTION_GENERATE 任务
-   SECTION_VALIDATE 任务
-   RENDER_EXPORT 任务

特点：

-   单章节单任务，避免长连接超时
-   支持并发控制（max_parallel_sections 可配置）
-   支持任务重试与幂等设计
-   通过 WebSocket / SSE 推送实时进度

注意：

LLM Gateway 保持短请求 RPC 风格，不引入二级异步队列。

------------------------------------------------------------------------

# 三、语义缓存安全设计

## 3.1 缓存类型分级

允许缓存：

1.  Embedding 缓存（sha256(text) → vector）
2.  Requirement 抽取结果缓存（同文档版本）

受限缓存（高约束）：

3.  合规条款回答缓存（仅模板化行业场景）

------------------------------------------------------------------------

## 3.2 缓存 Key 设计

cache_key =

industry_tag + tender_template_id + requirement_fingerprint +
evidence_fingerprint + schema_version

其中：

requirement_fingerprint = sha256(requirement_text) evidence_fingerprint
= sha256(sorted(evidence_ids))

------------------------------------------------------------------------

## 3.3 缓存失效规则

-   任一 evidence.valid_to \< today → 自动失效
-   schema_version 变更 → 自动失效
-   expert_doc 更新 → 关联缓存失效
-   项目敏感等级变化 → 失效

------------------------------------------------------------------------

# 四、数据库增强设计

## 4.1 修订轨迹机制

section_content 增加字段：

-   parent_section_id
-   origin (AI \| HUMAN \| MERGE)
-   edit_summary
-   created_by

可选增强：

新增 section_revision 表：

-   base_section_id
-   rev_no
-   editor
-   patch_diff
-   created_at

------------------------------------------------------------------------

## 4.2 Evidence 扩展字段

evidence_chunk 增加：

-   source_locator (JSON)
-   valid_to (date)
-   sensitivity_level

检索时默认过滤：

valid_to \>= today

若 30 天内到期：

生成阶段触发 NEED_HUMAN_INPUT 提示。

------------------------------------------------------------------------

# 五、LLM Gateway 增强策略

## 5.1 分级脱敏策略

PII（身份证/电话/邮箱） → 强制掩码\
商务价格 → 强制熔断\
敏感技术参数 → 项目级策略控制：

-   mask
-   allowlist
-   local_fill

------------------------------------------------------------------------

## 5.2 预算控制体系

### 项目级预算

project.token_budget_total project.token_budget_used

超出后：

-   阻断后续生成
-   返回 BUDGET_EXCEEDED

------------------------------------------------------------------------

### 任务级限制

-   每章节 max_input_tokens
-   每章节 max_output_tokens
-   retry_count \<= 2
-   fallback_count \<= 1

------------------------------------------------------------------------

## 5.3 审计新增字段

llm_call_log 增加：

-   budget_remaining
-   retry_count
-   fallback_count
-   cache_hit

# 六、可控多步 RAG（Schema 驱动）

## 6.1 多步流程

Step 1: Requirement 分解

输出 Schema：

{ sub_requirements: \[ { id, description, category } \] }

Step 2: 子问题检索

每个 sub_requirement 单独向量检索

Step 3: 证据合并

输出：

{ merged_evidence_ids: \[\], coverage_map: {} }

Step 4: 生成（证据强绑定）

Step 5: 确定性验证器校验

------------------------------------------------------------------------

## 6.2 严禁开放式 Agent

禁止模型：

-   自主检索任意来源
-   自主扩展任务边界
-   自由生成未绑定证据内容

所有步骤必须通过 JSON Schema 控制。

------------------------------------------------------------------------

# 七、默认阈值建议

-   覆盖率阈值：\>= 95%
-   MUST 条款未覆盖：直接阻断
-   单章节最大 tokens：16k
-   单项目预算默认：500k tokens
-   证据召回 TopK：5--8

------------------------------------------------------------------------

# 八、系统成熟度升级

v3.2 相比 v3.1：

-   增强可回滚能力

-   增强预算与成本治理

# 九、设计原则强化

1.  模型不具最终裁决权
2.  所有生成必须证据绑定
3.  缓存不得绕过验证器
4.  预算必须可控
5.  证据必须具时效管理
6.  异步架构必须可回溯
