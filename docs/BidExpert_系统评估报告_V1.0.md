# BidExpert 系统评估报告

> 评估视角：建设工程投标专家 + 商业AI操作使用专家
> 评估版本：release/V1.0
> 评估日期：2026-02-23

---

## 一、系统总体评价

BidExpert 是一个架构设计相当完整的 AI 辅助投标文件编制系统。技术栈选型合理（FastAPI + Qdrant + 多LLM适配），RAG 检索增强生成的思路正确，8阶段专家库入库流水线和多模型集成投票审查机制体现了工程化思维。但从建设工程投标实战角度看，系统在领域深度、质量保障和生产可靠性上存在显著短板。

---

## 二、功能评估

### 2.1 专家库建设（评分：70/100）

**优点：**
- 8阶段入库流水线（提取→摘要→富化→风险审查→合并→渲染→分块→持久化）流程完整
- 支持4类知识分类（规范、公司业绩、公司资质、项目管理人员资质及业绩）
- 混合检索（Dense + Sparse + RRF融合）方向正确
- 定价内容防护机制（`pricing_guard`）防止报价信息泄入知识库

**关键问题：**

1. **分类体系过于粗糙。** 实际投标中，专家库至少需要覆盖：施工方案模板库、安全文明施工方案库、质量保证体系库、应急预案库、类似工程业绩库、人员证书库、机械设备库、材料检测报告库、企业荣誉库等。当前4个分类无法支撑精细化的章节匹配。

2. **`quality_score` 硬编码为 `88.0`。** 结构化入库的知识片段统一给88分，完全没有基于内容时效性、完整度、与当前项目相关度的动态评分。这会导致过期业绩和新鲜业绩在检索中权重相同。

3. **稀疏向量实现不是真正的 BM25。** `_build_sparse_vector` 只做了词频（TF），没有逆文档频率（IDF）。对于投标领域，"施工方案"这种高频通用词和"110kV GIS组合电器"这种低频专业词会获得相似的检索权重，严重影响专业术语的召回精度。

4. **最小分块长度仅24字符。** 回退分块路径中，24个字符的中文文本（约12个汉字）几乎没有语义信息，会产生大量噪声片段污染检索结果。

5. **`pricing_guard` 误报率高。** 信号3（任意位置出现货币符号+数字即拦截）和信号4（数字密度计算用 `text.split()` 分词，中文无空格导致分母极小）会误拦大量含技术参数的合规文档。一份写着"RMB"的公司简介加上任何数字就会被拦截。

### 2.2 招标文件解析（评分：55/100）

**关键问题：**

1. **`build_tender_parsing_prompt` 对中国招标文件结构缺乏领域指导。** 没有区分资格预审文件、商务标、技术标、评标办法的不同解析策略。没有处理废标条款（一票否决项）与扣分条款的区别——这在实际投标中是生死攸关的。

2. **正则回退只识别5个关键词（`必须/应当/不得/需/必须满足`）。** 遗漏了大量实际招标文件中的强制性表述：`"否则作废标处理"`、`"不予通过资格审查"`、`"取消投标资格"`、`"加分项"`、`"优先考虑"`等。

3. **`build_global_facts_prompt` 只提取5个字段。** 缺少建设单位、监理单位、质量标准（鲁班奖/省优/合格）、安全文明施工等级要求、分包限制、工期节点要求、保证金要求等关键投标事实。这些遗漏会直接导致生成内容与招标要求不一致。

### 2.3 投标文件生成（评分：60/100）

**优点：**
- 多模型回退链 + 集成投票审查机制设计合理
- 全局事实冲突检测（`_global_fact_conflict_warnings`）会强制人工介入
- 证据有效期检查（`_expiry_warnings`）防止引用过期材料
- 语义缓存减少重复调用

**关键问题：**

1. **`build_section_generation_prompt` 没有章节类型区分。** 施工方案、项目管理机构配备、质量保证体系、安全文明施工方案、工期保证措施——这些章节的结构、深度、专业术语要求完全不同，但当前用同一个通用prompt生成所有章节。这是最大的质量风险。

2. **`build_review_prompt` 缺乏领域审查清单。** 没有检查：工期是否与招标文件一致、项目经理证书编号是否与全局事实匹配、业绩日期是否在有效期内、技术参数（电压等级/容量/型号）是否与招标文件吻合、是否遗漏了废标条款要求的必备内容。

3. **`section_max_output_tokens=4000`。** 对于施工组织设计等核心技术标章节，4000 token（约2000-3000汉字）远远不够。一个完整的施工方案通常需要8000-15000字。

4. **回退草稿模板过于简陋。** 当所有LLM都失败时，`_compose_draft` 只是拼接前3条证据的首句，生成的内容完全不可用。

### 2.4 使用便捷度（评分：75/100）

**优点：**
- 6面板工作流设计（专家库→招标分析→投标编制→审查评分→排版→归档）符合投标工作流程
- BYOK 支持用户自带API密钥，降低使用门槛
- 预览→确认的两阶段入库机制让用户有审核机会
- 4窗格编辑器（用户输入/证据/AI草稿/终稿）设计合理

**问题：**
- `app.js` 单文件115KB，前端无框架，状态全局可变——后续维护和功能扩展会越来越困难
- 前端无输入校验，完全依赖后端，用户体验不佳（提交后才知道格式错误）
- API Key 明文存储在 localStorage，存在安全隐患

## 三、使用中可能出现的问题及解决办法

| 问题 | 根因 | 解决办法 |
|------|------|----------|
| 专家库入库时合规技术文档被误拦 | `pricing_guard` 信号3/4误报率高，中文分词逻辑有缺陷 | 信号3改为上下文窗口检测（与信号2一致）；信号4用 jieba 分词替代 `text.split()` 计算密度 |
| 生成的施工方案内容过短、结构不完整 | 输出token上限4000，无章节类型区分 | 按章节类型设置不同的 `max_output_tokens`（施工方案≥12000，人员配备≥4000）；为每类章节编写专用prompt模板 |
| 检索到的知识片段与当前项目不相关 | 稀疏向量无IDF，quality_score硬编码 | 实现真正的BM25（加入IDF）；基于时效性、项目类型匹配度动态计算 quality_score |
| 遗漏废标条款导致投标无效 | 招标解析prompt和正则都未覆盖废标条款 | 增加废标条款专项提取逻辑，在生成前强制校验所有废标条款是否已响应 |
| 项目经理信息、工期等与招标文件不一致 | `global_facts` 只提取5个字段，审查prompt无领域清单 | 扩展全局事实提取至15+字段；审查prompt增加领域一致性检查清单 |
| OCR识别扫描件质量差 | Tesseract对中文表格识别率低 | 优先使用商业OCR（TextIn/DocAI），设置OCR置信度阈值，低于阈值标记为需人工校对 |
| 全部LLM提供商同时不可用 | 回退草稿质量极低 | 维护一套离线章节模板库，LLM全部失败时用模板+关键词替换生成可编辑的基础框架 |
| 配置错误导致生产环境启动失败 | `MASTER_KEY_B64` 未设置无启动校验，`gemini-3-pro` 模型名不存在 | `validate_runtime_baseline()` 增加 master key 和模型名有效性校验 |

## 四、确保质量符合要求的详细建议

### 4.1 专家库质量保障

1. **细化知识分类体系。** 建议扩展为至少10个分类：
   - 施工方案模板（按工程类型：输变电/配电/土建/安装）
   - 质量保证体系文件
   - 安全文明施工方案
   - 应急预案
   - 类似工程业绩（含合同金额、竣工时间、获奖情况）
   - 项目管理人员资质证书
   - 主要机械设备清单
   - 材料检测报告/合格证
   - 企业资质证书
   - 企业荣誉/获奖

2. **实现动态质量评分。** 替换硬编码的 `88.0`，基于以下维度计算：
   - 时效性（距今年限，业绩超过5年降权）
   - 完整度（关键字段是否齐全）
   - 项目类型匹配度（电压等级、工程类别是否匹配）
   - 来源可信度（正式合同 > 内部总结 > 网络资料）

3. **建立知识库定期审查机制。** 设置 `valid_to` 自动过期提醒，资质证书到期前30天预警，业绩超过有效年限自动降权或标记。

4. **入库前增加人工抽检环节。** 对LLM结构化转换的结果，按比例（建议10-20%）抽检，记录准确率，低于阈值时触发全量人工审核。

### 4.2 AI生成质量保障

1. **建立章节类型专用prompt体系。** 这是最关键的改进。每类章节需要独立的：
   - 结构模板（如施工方案必须包含：工程概况→施工部署→施工方法→质量保证→安全措施→工期保证→环保措施）
   - 专业术语词表
   - 输出长度要求
   - 必须引用的证据类型

2. **实现废标条款前置校验。** 在生成前：
   - 专项提取所有废标条款和一票否决项
   - 生成后逐条校验是否已响应
   - 未响应的废标条款必须阻断流程，强制人工处理

3. **增强合规审查prompt。** 当前审查只有通用的 severity/type/location 结构，需要增加：
   - 工期一致性检查（生成内容中的工期 vs 招标文件要求）
   - 人员信息一致性（证书编号、职称、业绩）
   - 技术参数一致性（电压等级、设备型号、容量）
   - 格式合规性（是否满足招标文件的格式要求）
   - 废标条款覆盖率（100%才能通过）

4. **引入分级人工审核。** 建议设置三级审核：
   - 自动通过：合规审查 PASS + 所有废标条款已覆盖 + 无全局事实冲突
   - 人工复核：ADJUST_PASS 或存在 warnings
   - 强制重写：REWRITE 或废标条款未覆盖

### 4.3 检索质量保障

1. **实现真正的 BM25。** 当前的 TF-only 稀疏向量对投标领域的专业术语区分度不够。需要维护语料级别的 IDF 统计，让"110kV GIS组合电器"这类低频专业词获得更高权重。

2. **增加领域同义词表。** 投标文件中同一概念有多种表述（如"项目经理"/"项目负责人"/"现场负责人"），需要在检索时做同义词扩展。

3. **优化 rerank 权重。** 当前 `base_score*0.55 + overlap*0.40 + quality*0.05`，quality 权重过低。建议根据实际检索效果 A/B 测试调整。

### 4.4 工程化保障

1. **测试覆盖率严重不足。** 当前430行测试代码覆盖9个文件，核心服务层（expert_library、generation_pipeline、qdrant_store、llm_gateway）零单元测试。建议优先补充：
   - `pricing_guard` 的中文文档误报测试
   - `tender_parser` 的废标条款识别测试
   - `generation_pipeline` 的全局事实冲突检测测试
   - `qdrant_store` 的混合检索准确率测试

2. **建立投标文件质量基准测试集。** 收集10-20份真实的招标/投标文件对，建立自动化评估：
   - 废标条款覆盖率（目标：100%）
   - 评分项响应率（目标：≥95%）
   - 技术参数一致性（目标：100%）
   - 生成内容与证据的可溯源率

3. **修复已知的配置和代码问题：**
   - `gemini-3-pro` 模型名修正
   - `DraftGenerationResponse` 中硬编码的 gemini 默认值
   - `CompletedBid.project_id` 缺少外键约束
   - `MASTER_KEY_B64` 启动校验

## 五、总结

BidExpert 的系统架构和工程化水平在同类产品中属于中上水平，RAG + 多模型集成投票 + 定价防护的技术路线是正确的。但当前版本距离"可信赖地用于真实投标"还有明显差距，核心瓶颈不在技术架构，而在**领域深度不足**——prompt缺乏投标专业知识、知识分类过粗、废标条款无专项处理、章节生成无类型区分。

**最高优先级的三件事：**
1. 为每类投标章节建立专用prompt模板和结构约束
2. 实现废标条款的专项提取和前置校验机制
3. 修复 `pricing_guard` 的中文误报问题

这三项改进完成后，系统的实用价值会有质的提升。
