# BidExpert V1.0 部署上线前审核报告

审核日期：2026-02-23 | 分支：`release/V1.0`

---

## 一、总体评价

BidExpert 是一套面向建设工程招投标场景的 AI 辅助投标文书生成系统，覆盖"专家库建设 → 招标文件解析 → 投标文书生成 → 合规审查 → 模拟评分 → Word 排版导出"六步全流程。架构设计合理（FastAPI + PostgreSQL + Qdrant + Redis/Celery + 多模型网关），核心管线已实现，但距离生产级部署仍有明确差距。

**结论：当前版本不建议直接上线生产环境。** 需完成下述 P0 阻塞项后方可进入 Go/No-Go 评审。

## 六、招投标业务视角评价

从建设工程招投标实务角度：

1. **废标风险控制不足** — 系统缺少废标条款提取和生成前校验机制。在实际投标中，遗漏一个"必须提供"的资质证明就可能导致废标，这是最高优先级的业务风险。

2. **章节生成质量不达标** — 施工组织设计、技术方案等核心章节需要 8000-15000 字的结构化输出，当前 4000 token 上限远远不够。且所有章节使用同一个 prompt 模板，无法满足不同章节类型（技术方案 vs 商务偏差表 vs 人员配置表）的结构要求。

3. **评分模拟可信度存疑** — 在无审查报告时使用 token 重叠率估算分数，可能给用户虚假的信心。建设工程评标通常采用综合评估法或经评审的最低价法，当前评分逻辑与实际评标规则的对应关系不明确。

4. **pricing_guard 误报影响可用性** — "元""需"等单字匹配会将大量正常技术文档标记为含价格信息并过滤，直接影响专家库入库质量和生成内容的完整性。这在建筑工程领域尤为严重，因为"单元""构件""元器件"等词汇极为常见。

5. **招标文件解析能力薄弱** — 仅 5 个正则关键词无法覆盖招标文件的复杂结构（资格要求、评分标准、技术规格、合同条款等），LLM 提取路径对大文档无分块策略。

## 七、上线建议

### 阻塞项（必须完成才能上线）

1. 修复 2 个 CRITICAL 安全问题（数据库/缓存默认密码）
2. 修复 JWT `exp` 强制校验
3. 修复 `scoring_engine.py` 空值崩溃
4. 修复 detached ORM 对象问题（review_engine + scoring_engine）
5. 修复 `pricing_guard` 中文误报（至少将"元"改为"元/万元/亿元"等货币量词组合）
6. 统一 Python 版本（容器与开发环境）
7. 覆盖率门槛提升至 80% 并补充核心路径测试

### 建议优先完成（上线后首个迭代）

1. 章节类型差异化 prompt 模板（施工方案、技术规格、人员配置等）
2. 废标条款提取与生成前校验
3. 招标文件 LLM 解析分块策略
4. 前端模块化拆分（至少按功能域拆为 5-6 个模块）
5. API Key 从 localStorage 迁移到 httpOnly cookie 或 session 存储

### 可延后

前端状态管理重构、Qdrant 认证、容器只读文件系统、稀疏向量 IDF 增强等。

---

**审核结论：V1.0 架构设计合理，核心管线已通，但安全加固和业务质量两个维度存在明确的阻塞项。建议完成上述 7 项阻塞修复后，重新进行 Go/No-Go 评审。预计修复工作量 3-5 天。**
